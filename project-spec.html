OmniMart — Ratings & Reviews (POC)

Living specification for a Go proof-of-concept of an enterprise-grade ratings & reviews platform, exposing two physically separate API surfaces (site-facing and internal).

Status: POC Version: 1.0Updated: 2026-06-11 Owner: @shubhambakreStack: Go 1.25

OmniMart is a fictional retailer used as the example tenant. The architecture is vendor-neutral; no real-world brand is implied.

01 Executive summary

A runnable Go POC for an enterprise ratings & reviews service with two physically separate listeners: a site-facing API on :8080 (public shoppers/edge) and a non-site-facing internal API on :8081 (moderation, ingest, ops). It demonstrates production-shaped architecture (hexagonal layering, aggregate caching, idempotency, cursor pagination, a review state machine) while keeping dependencies minimal — stdlib-only in in-memory mode, plus an optional pure-Go SQLite backend.

◆ Decision — two listeners, not one
Different ports → different middleware stacks → no accidental crossover. In production these terminate in different network zones (CDN/WAF vs. service mesh + mTLS). The POC encodes that separation from day one.

02 Problem statement

Ratings & reviews is read-heavy on the storefront and write/moderation-heavy internally, with strict rules about what can be shown publicly. Conflating these surfaces invites accidents — e.g. exposing a moderation queue on a public route.

▲ Failure mode to design out
"A public route accidentally exposed the moderation queue" — the kind of incident that ends up on a postmortem.

03 Goals

● G1 — Surface separation
Physically separate public vs. internal APIs with distinct auth and middleware.
● G2 — Correct read/write asymmetry
Public reads return only APPROVED; pending/rejected never leak.
● G3 — Production-shaped seams
Hexagonal layering + an aggregate-recompute seam ready for async (Kafka) aggregation.
● G4 — Reliability primitives
Idempotency keys, cursor pagination, graceful shutdown, sane timeouts.

04 Non-goals

  • Not production-ready persistence (in-memory default; SQLite is a step up, not Cassandra/Redis).
  • Not real identity — auth is stubbed via X-Customer-Id / X-Api-Key headers.
  • Not real moderation ML — a word-list stands in for an async moderation service.
  • No rate limiting, metrics endpoint, or event publishing yet (documented upgrade path).

09 Architecture overview

Hexagonal: domain → repository (interface) → service → transport. Two HTTP handlers (site/internal) share the service layer but never the listener.

:8080 site handler┐service→repository (interface)→memory | sqlite
:8081 internal handler┘→ same service, different middleware/auth
◆ Decision — aggregate cache seam
RatingSummary lives in its own store, recomputed on approval. The RatingService.Recompute seam is exactly where a Kafka review.approved consumer would plug in for debounced async aggregation.

11 Main workflows

W1 — Submit → moderate → publish

Shopper POSTs a review (idempotent) → auto-approve if clean, else PENDING → moderator approves on :8081 → aggregate recomputed → review appears in public reads.

W2 — Hot read path

Storefront lists approved reviews via cursor pagination (stable under concurrent writes).

15 Risks & assumptions

▲ R1 — Surface crossover
A public route exposing internal data. Mitigation: separate listeners + middleware (built-in).
▲ R2 — Aggregate staleness
Inline recompute won't scale. Mitigation: recompute seam ready for async Kafka consumer.
▲ R3 — POC mistaken for prod
Stubbed auth/storage shipped as-is. Mitigation: explicit "stubbed → production" table.

Assumptions: Go 1.22+; single instance for the POC; trusted internal network for :8081.
